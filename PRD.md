# Content Pipeline PRD

_Generated by multi-agent debate on 2026-03-19. Owner: Justin (drinkYourOJ)._

## Executive Summary

The OJ Content Engine is a two-host content pipeline that discovers trending topics across RSS, Reddit/HN, and Twitter/X, scores them against a 6-dimension brand-aware rubric, generates platform-specific drafts with voice-drift protection, and stages them in Notion for Justin's review. The system splits cleanly: long-running discovery, scoring, and generation run on a Worker host (FastAPI + ARQ on Railway/Fly.io), while the approval UI and lightweight API routes run on Vercel (Next.js App Router). A mandatory thesis injection step between triage and generation ensures every piece of content is anchored in Justin's original thinking, not just AI-generated trend summaries.

## 2. Trend Discovery Layer

**Host:** Worker

### Sources

| Source | Method | Frequency | Fallback |
|--------|--------|-----------|----------|
| RSS/Newsletters | `feedparser` against curated OPML (~30 feeds) | Every 4 hours | Remove dead feeds from OPML; no external dependency |
| Reddit | JSON API (public, no OAuth): r/depin, r/cryptocurrency, r/singularity, r/selfhosted | Every 1 hour | Switch to `praw` with OAuth if JSON API breaks |
| Hacker News | Algolia API (search + top stories) | Every 1 hour | HN Firebase API as secondary |
| Twitter/X | Twitter API v2 (Basic tier) on curated lists | Every 2 hours | Nitter RSS bridges; degrade gracefully to RSS-only |

### Polling Strategy

- Each source runs as an independent ARQ cron job on staggered schedules
- Deduplication: URL hash + title similarity (Levenshtein > 0.85 = duplicate)
- Velocity scoring for Reddit/HN: `upvotes / hours_since_post`
- All raw signals written to `signals` table in Postgres
- Redis pub/sub notifies the scoring stage of new signals

### Fallback Behavior

- Each poller is fully independent — one dying does not affect others
- Dead source detection: 3 consecutive runs returning 0 results triggers an alert in `system_alerts` table
- Alert surfaces in the Vercel UI health dashboard
- No cascading failures by design

### Data Schema: `signals` Table

| Column | Type | Description |
|--------|------|-------------|
| `id` | UUID | Primary key |
| `source` | TEXT | rss, reddit, hn, twitter |
| `url` | TEXT | Source URL |
| `title` | TEXT | Signal title |
| `body_preview` | TEXT | First 500 chars |
| `discovered_at` | TIMESTAMPTZ | When the poller found it |
| `source_metrics` | JSONB | Upvotes, comments, shares, velocity |
| `dedup_hash` | TEXT | SHA-256 of normalized URL |

## 3. Topic Triage Rubric

### Scoring Dimensions

| Dimension | Weight | Scale | Scoring Logic |
|---|---|---|---|
| **Signal Strength** | 25% | 0-100 | 1 source = 10, 2 independent = 40, 3+ = 70, 3+ cross-platform = 100 |
| **Timing Window** | 15% | 0-100 | Evergreen = 30, 1-week = 50, 48-72hr = 80, Breaking = 100* |
| **Depth Potential** | 15% | 0-100 | Hot take only = 20, thread-worthy = 50, long-form + thread = 80, series = 100 |
| **Novelty** | 15% | 0-100 | Saturated = 0, slight angle = 40, clear gap = 70, untaken territory = 100 |
| **Community Resonance** | 10% | 0-100 | No overlap = 0, tangential = 30, direct = 60, core territory = 100 |
| **Brand Angle Availability** | 20% | 0-100 | No unique angle = 0, generic take = 20, contrarian exists = 60, thesis-advancing = 100 |

### Hard Gates (auto-reject regardless of composite score)

- **Community Resonance < 20** — Topic has no connection to DePIN, decentralized infra, AI tooling, or adjacent spaces
- **Brand Angle Availability < 20** — No drinkYourOJ-specific angle exists; would produce generic content

### Conditional Cap

- **Timing "Breaking"** scores 100 only if **Novelty >= 50**; otherwise capped at 70. Prevents rushing to publish without a unique angle.

### Threshold Logic

| Composite Score | Action |
|----------------|--------|
| >= 65 | Queued for thesis injection + content generation |
| 55-64 | Flagged for Justin's manual review |
| < 55 | Auto-archived (logged in Postgres, not deleted) |

### Scoring Implementation

- **Pass 1 (rule-based, zero LLM cost):** Computes Signal Strength, Timing Window, and Community Resonance using source count, age-based decay, and keyword taxonomy matching
- **Pass 2 (LLM-assisted, Claude Haiku):** Assesses Depth Potential, Novelty, and Brand Angle Availability. Only runs for signals with Pass 1 pre-filter score > 30. Structured JSON output.
- **Scoring adjustments:** `scoring_adjustments` table allows Justin to create per-keyword/topic dimension adjustments (-20 to +20) from the review UI. Checked in Pass 1 before LLM scoring.

### Brand Filter Rules

Topics must clear both hard gates to enter scoring. The Brand Angle dimension (20% — heaviest single weight) ensures that trend strength alone cannot push a topic through. Every topic that reaches content generation has a documented brand angle.

## 4. Content Generation Pipeline

**Host:** Worker

### Stage-by-Stage Architecture

#### Stage 2: Signal Scoring (Worker)

- Two-pass scoring system (rule-based pre-filter + Claude Haiku for subjective dimensions)
- Cost: ~$0.006/day at 50 signals/day
- Failure: Queue in Redis with `pending_scoring` status, ARQ retries with exponential backoff (max 3 attempts)
- Data: `signals` -> `scored_signals` table (adds `score_breakdown` JSONB, `composite_score` numeric)

#### Stage 3: Topic Triage (Worker)

- Mechanical rubric application on scored data
- Applies hard gates, conditional cap, threshold logic
- Data: `scored_signals` -> `topics` table (`status`, `queued_at`, `reviewed_by`, `review_decision`, `thesis`)
- Queued/review topics push notification to Upstash Redis

#### Stage 3.5: Thesis Injection (Vercel UI -> Worker reads)

- After triage queues a topic (>= 65) or Justin manually approves (55-64), a notification fires
- UI presents: topic title, score breakdown, thesis input field ("What's your take? 2-3 sentences")
- Justin's options:
  - **Write thesis** -> stored in `topics.thesis`, topic moves to generation queue
  - **Skip** -> generates with `thesis_provided: false`, drafts flagged "AI-originated — heavy edit needed"
  - **Snooze 24h** -> re-notification
  - **Kill** -> topic archived
- Generation prompt anchors on thesis: *"The core argument of this piece is: [thesis]. Build the analysis around this thesis."*

#### Stage 4: Content Generation (Worker)

**Prompt Architecture (3-layer):**

1. **System prompt:** Brand voice bible (verbatim from brand spec), platform-specific constraints, hard-no list as negative examples
2. **Context injection:** Topic signal data, score breakdown, 3 similar past Notion articles (by title similarity), 3-5 randomly-selected voice exemplars from `voice_exemplars` table
3. **Generation prompt:** Platform-specific instructions + Justin's thesis (if provided)

### Voice Injection Points

1. **Voice exemplar corpus** — 10-15 curated posts stored in Postgres `voice_exemplars` table. 3-5 randomly selected per generation run. Justin manages via `/dashboard/settings/exemplars`. Refreshed quarterly.
2. **Brand voice bible** — System prompt includes the complete brand spec: voice description, hard-no list, platform-specific tone guidelines
3. **Thesis anchor** — Justin's 2-3 sentence take (when provided) becomes the structural backbone of the generated content
4. **Voice-drift self-critique** — Dedicated second pass for Substack long-form: *"You are a drinkYourOJ subscriber who has read every post since 2023. Read this draft. Flag every sentence that sounds like it could appear in a generic tech newsletter, a press release, or a crypto hype blog. For each flagged sentence, explain why it's off-brand and rewrite it in Justin's voice: dry, direct, systems-thinking, occasionally funny, never breathless."*

### Platform-Specific Branches

Each platform branch is an independent ARQ task. Partial success is acceptable — Justin reviews whatever completed.

**Model:** Claude Sonnet for all generation (quality bottleneck — Haiku insufficient for voice work). Cost: ~$0.08/topic across all 4 platforms.

## 5. Per-Platform Output Specs

### Substack (Long-Form)

- **Length:** 1,500-2,500 words
- **Process:** Draft -> voice-drift self-critique -> revised draft (two-pass)
- **Structure:** Strong hook (earns the read), systems-thinking analysis, contrarian or non-obvious conclusion
- **Tone:** Intellectual stand-up comedy. Dry, direct. Complex ideas explained simply without dumbing down. Humor to land the knife.
- **Hard-no:** No "here's what you need to know" framing, no breathless AI hype, no listicle structure

### Twitter/X (Threads)

- **Length:** 5-12 tweets, each <= 280 characters
- **Structure:** Hook in tweet 1 (must stop the scroll), substance in tweets 2-10, CTA in final tweet
- **Tone:** Punchy, opinionated, occasionally funny. A thread of *thoughts*, not bullet points
- **Hard-no:** No thread-of-bullet-points, no "1/ Let me tell you about X" generic openers

### LinkedIn (Thought Leadership)

- **Length:** 300-600 words
- **Structure:** Opening hook, 3 insight paragraphs, closing thought
- **Tone:** Honest takes on building, decentralization, tech. Not hustle-porn, not corporate glaze
- **Hard-no:** No cringe inspiration, no "I'm humbled" framing, no engagement bait

### Instagram (Visual-First)

- **Length:** Caption 150 words max + image card prompt
- **Structure:** Conceptual visual (diagram, quote card, data visualization) + concise caption
- **Tone:** Visual carries the weight. Caption adds context, doesn't repeat what the image shows
- **Hard-no:** No selfie-with-caption format, no walls of text, no generic stock imagery
- **Image card:** Generated via prompt -> uploaded to Vercel Blob, URL stored in draft metadata

## 6. Notion Staging Schema

**Host:** Worker writes, Vercel reads

### Page Properties

| Property | Type | Values/Description |
|----------|------|-------------------|
| Title | Title | `[Platform] Topic Name` (e.g., `[Substack] Helium's Quiet Infrastructure Play`) |
| Platform | Select | Substack, Twitter, LinkedIn, Instagram |
| Status | Select | Draft, Review, Approved, Published, Killed |
| Composite Score | Number | 0-100 |
| Score Breakdown | Rich Text | Per-dimension scores |
| Generated At | Date | Timestamp |
| Topic ID | Text | Links back to Postgres `topics` table |
| Brand Angle | Rich Text | The angle identified during scoring |
| Thesis Provided | Checkbox | Whether Justin wrote a thesis anchor |
| Model Used | Text | e.g., claude-sonnet-4-5 |
| Token Cost | Number | Approximate cost in USD |

### Page Body

The draft content, formatted for the target platform. Substack drafts include the full article. Twitter drafts include numbered tweets. LinkedIn drafts include the formatted post. Instagram drafts include caption + image card URL.

### Page Comments

Generation metadata: model version, prompt version, generation timestamp, token usage breakdown.

### Approval UX

- Notion pages are the source of truth for content editing
- Justin edits directly in Notion (the approval UI links to the Notion page)
- Status changes in the approval UI sync bidirectionally with Notion page status
- If Notion is down, drafts surface from Postgres as a fallback

### Rate Limiting

Notion API limit: 3 requests/second. ARQ tasks batch with 400ms delays between API calls.

## 8. Tech Stack Decisions

### Vercel Layer

| Technology | Purpose | Rationale |
|------------|---------|-----------|
| **Next.js App Router** | Approval UI + API routes | Native Vercel deploy, SSR for dashboard, API routes for lightweight ops |
| **Vercel Postgres (Neon)** | Structured data (signals, scores, topics, drafts) | Native Vercel integration, serverless-compatible, branching for dev |
| **Upstash Redis** | Notification badges, pub/sub signals | Serverless Redis, Vercel-native, no self-hosted container |
| **Vercel Blob** | Image card storage for Instagram | First-party file storage, up to 5TB |

### Worker Layer

| Technology | Purpose | Rationale |
|------------|---------|-----------|
| **FastAPI** | HTTP API for worker, webhook endpoints | Justin's preferred stack, async-native, lightweight |
| **ARQ** | Async task queue + cron scheduling | Redis-backed, Python-native, simpler than Celery for a solo dev |
| **Docker** | Worker containerization | Reproducible env for pollers + Playwright |
| **Playwright** | Substack automation (publish step) | Already established in Justin's workflow |
| **Claude API (Haiku)** | Signal scoring (Depth, Novelty, Brand Angle) | $0.006/day — cheapest model sufficient for classification |
| **Claude API (Sonnet)** | Content generation + voice-drift critique | Quality bottleneck — Haiku can't write in voice. ~$0.08/topic |
| **Notion API** | Page creation, status sync, context retrieval | Target staging system, bidirectional linking |

### Shared Infrastructure

| Technology | Used By | Purpose |
|------------|---------|---------|
| **Neon Postgres** | Both hosts | Single source of truth for all pipeline data |
| **Upstash Redis** | Both hosts | Pub/sub between worker stages, notification badges for Vercel UI |

### Key Rationale Notes

- **Why not Vercel Functions for polling/generation:** Hard 10-60s timeout. Polling runs continuously, generation takes 30-120s per platform. These must live on the worker.
- **Why not Celery for task queue:** ARQ is simpler, Redis-backed (same Upstash instance), and sufficient for a solo dev. Celery is over-engineered for this scale.
- **Why Haiku for scoring, Sonnet for generation:** Cost optimization. Scoring is classification (Haiku handles it). Generation requires voice matching (Sonnet required). Total daily LLM cost: < $1.
- **Why shared Postgres instead of worker-local DB:** Single source of truth. The Vercel UI needs to read scoring data and draft status — having two databases creates sync headaches.

## 10. Open Questions / Future Scope

### Deferred to v0.3+

- **Fast-track generation:** Topics scoring >= 85 composite auto-generate without thesis (AI-originated flag). Prevents losing breaking-trend windows while Justin sleeps. _(SCOUT proposal, JUDGE deferred)_
- **Rejection-to-scoring feedback automation:** Currently manual (Justin creates adjustments from review UI). Could auto-suggest adjustments based on rejection patterns.

### Deferred to v1.0

- **Mandatory thesis for Substack:** BRAND argues long-form demands Justin's actual thinking — skip-thesis path should be disabled for Substack specifically. _(BRAND proposal, JUDGE deferred to v1.0)_
- **A/B testing on voice exemplar selection:** Does random selection outperform curated rotation? Measure via approval rate.

### Future Scope (Post v1.0)

- **Auto-publish pipeline:** Playwright automation for Substack is established. Extend to Twitter (API), LinkedIn (API), Instagram (API or Buffer integration). Remove manual publish step.
- **Analytics feedback loop:** Connect platform analytics (Substack opens, Twitter impressions) back to scoring model. Topics that generate high-engagement content should boost similar future topics.
- **Multi-author support:** If drinkYourOJ expands to guest writers, the pipeline needs per-author voice exemplar sets and thesis paths.
- **Webhook-based discovery:** Instead of polling, accept inbound signals from Zapier/IFTTT or custom integrations (Discord bot watching DePIN channels, Telegram group monitors).
- **Cost dashboard:** Track LLM spend per topic, per platform, per week. Alert if daily spend exceeds threshold.
